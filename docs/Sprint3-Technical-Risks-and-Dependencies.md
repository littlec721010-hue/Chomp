## Trigger → Recovery Procedure → Beta Prevention

The following procedures operationalize the supplied Sprint 2 summary. They are proposed runbook steps, not evidence that recovery has already been exercised.

| Risk | Trigger | Recovery procedure | Beta prevention |
| --- | --- | --- | --- |
| Branch drift / merge conflict (R13) | A PR conflicts, shared types diverge, or an integrated change breaks another flow. | Pause the affected merge; preserve work; compare against the accepted baseline; resolve with affected owners; rerun checks and the impacted flow before resuming. | Small PRs, one named integration coordinator, explicit ownership of shared files and review of contract changes. |
| Dependencies / Metro (R10–11) | Frozen install, typecheck, tests or Metro/Web export fails after dependency/tool changes. | Capture the error and versions; reproduce with the committed lockfile and agreed toolchain; isolate the offending change; propose a reviewed correction or revert. Do not blindly regenerate the lockfile. | Standardize Node 24, pnpm 11.25.0 and Expo ~57; use frozen installs and repeatable CI/CLI typecheck, tests and export. Historical Alpha checks used Node 23.10.0 and do not establish a Node 24 test pass. |
| Supabase / isolation (R01–02) | Verification/login fails, preview data appears in a live account, or a direct cross-account request exposes/changes another account's data. | Stop the affected live flow; reproduce with test accounts; inspect callbacks, identity and policies; correct configuration/policies through review; rerun A/B and anonymous isolation checks before reopening. | Separate preview AsyncStorage/fixtures from real-mode backend data; apply migrations and owner/member policies; test with normal client credentials before accepting live login. |
| Restriction mismatch / safety labels (R09, R14) | An alias is not normalized, an unsupported restriction disappears, or no-match output becomes selectable through relaxed filters. | Preserve the original restriction; block misleading compatibility/selection; correct the adapter/labels and add a regression case; retest individual/group no-match states. | Reviewed canonical/alias mapping; explicit unsupported states; never silently relax allergen/dietary constraints; distinguish fixtures from verified data. |
| Partial vote / stale room (R03–04) | Connection loss, conflicting updates, duplicate votes or inconsistent completion/counts across clients. | Mark state as reconnecting/unconfirmed; reauthenticate if needed; reload authoritative membership/votes; reconcile or retry valid pending actions without duplicates; recompute results only after the agreed completion rule holds. | Server-coordinated lifecycle and authorized constrained writes; reconnect validation, subscription cleanup and concurrent two-device tests. |
| Receipt arithmetic / OCR error (R06–08) | Recognition omits/misreads items, printed totals disagree, or computed shares do not reconcile. | Keep the OCR bill as a review draft; allow corrections/additions/removal; resolve amounts before confirmation/save. On failure offer retry/reselect/cancel and preserve edits; independent entry is deferred. | Real OCR → editable review → confirm → equal split → save; integer cents; clear amount/rate units and tax/tip precedence; exact remainder allocation and persisted corrected values. |
| Invalid restaurant route (R14) | Unknown/deleted/malformed restaurant ID reaches a result route. | Show an unavailable/not-found state with a route back to recommendations; do not substitute the first restaurant or add it to history. | Validate route IDs at the data boundary and test direct links and stale history references. |

## Integration dependencies and recommended order

Confirmed primary Split flow: photograph/upload a receipt → real OCR populates an editable bill → user reviews and edits recognized items, adds missing items and removes incorrect items → user confirms the corrected bill → calculate exact-cent equal shares → save. Correction and missing-item entry remain required. Scope revision October 21, 2026: independent no-OCR manual entry is deferred pending usability feedback, superseding its earlier mandatory status. OCR and user corrections must feed the same bill model and calculation rules.

- Designate a Supabase project maintainer and confirm who can apply migrations/configure email and callbacks; do not put secret keys or user credentials into this document or evidence.
- Assign named backend/group/persistence/OCR/QA owners. Proposed role coordination above is not a claim that any teammate accepted work.
- Confirmed completion/tie rule: wait for all required votes; draw only among tied highest-vote restaurants; server finalizes/persists once per round, shows a tie notice and serves the same result to both clients after retry/refresh/reconnect. Remaining decisions: required-member snapshot, leave/close, post-finalization edits/new rounds and synchronization target (5 seconds remains proposed).

R04 follow-up: current `winningRestaurant` breaks equal vote counts by rating and is local-only. This does **not** satisfy the newly confirmed random tie policy. When development resumes, replace that policy through reviewed backend-authoritative finalization with concurrency/idempotency protection and persisted winner/tie metadata. Failure recovery reads the saved round result; it must not recompute or redraw on each client. Tie rules are resolved planning decisions; implementation, lifecycle edge rules and verification remain open. See GROUP-04 and GC-06.
- Select OCR implementation, supported receipt language/formats and representative accuracy set/target. Do not infer that manual fallback removes the real-OCR requirement.
- Agree whether receipt images need to be retained. If stored, define owner-only access, retention and deletion; do not assume image storage is necessary just to persist structured bills.
- Reserve devices, two verified test accounts and at least three user/stakeholder sessions; record the final deployment's commit and environments.
